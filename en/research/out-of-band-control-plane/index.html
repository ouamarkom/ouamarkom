PART I - EXECUTIVE AND RESEARCH FOUNDATION

1. Executive Summary

OUAMARKOM™ proposes the investigation and engineering development of an Out-of-Band Control Plane architecture for governing economic actions initiated by AI agents.

The proposed architecture separates an AI agent's reasoning environment from an independently governed authorization and enforcement path.

Its central premise is that the capability to reason about, recommend, or initiate an economic action should not, by itself, confer authority to execute that action.

The proposed Control Plane is designed to evaluate identity, delegated economic authority, policy constraints, execution eligibility, revocation status, and relevant operational conditions before an economic action is permitted to reach an external execution system.

An Execution Gateway is responsible for enforcing the resulting decision at the execution boundary.

An Evidence and Verification subsystem records the lifecycle of the action and evaluates whether the resulting external outcome can be independently substantiated.

The architecture will be developed and evaluated through the OUAMARKOM™ Smart Hand experimental environment and the Governed Economic Action Benchmark (GEAB).

The objective is not merely to demonstrate that an authorization service can reject an invalid request. It is to determine whether an independently enforced control architecture provides measurable advantages over alternative governance designs, particularly in:

  • Unauthorized execution prevention.
  • Delegated authority enforcement.
  • Cumulative budget control.
  • Concurrent action management.
  • Revocation enforcement.
  • Execution-path integrity.
  • Duplicate execution prevention.
  • Evidence completeness.
  • Outcome verification.
  • Operational latency and overhead.
The architecture remains a proposed engineering design until its components are implemented, tested, and evaluated against defined baselines.

2. Purpose

This document establishes the proposed architecture, component responsibilities, interfaces, lifecycle states, experimental scenarios, performance indicators, acceptance criteria, and evidence requirements for the OUAMARKOM™ Out-of-Band Control Plane.

3. Research Context

The architecture is developed within the CE-AI™ research framework (Command Economy of AI).

CE-AI™ investigates the relationship between commands, delegated authority, governed execution, and verifiable economic outcomes.

The Out-of-Band Control Plane is a proposed architectural approach within this research direction.

The research distinguishes four separate concepts:

  • Capability: What an AI agent can reason about or technically attempt.
  • Authority: What the agent is institutionally permitted to do.
  • Execution: Whether the permitted action is actually carried out.
  • Verification: Whether the resulting outcome can be substantiated through appropriate evidence.

These concepts must not be treated as interchangeable.

4. Core Architectural Principle

Separation of Reasoning from Independent Economic Authority Enforcement

The AI agent may formulate an economic action request, but it must not be the sole authority responsible for determining whether that request is permitted.

The proposed architecture assigns:

  • Reasoning to the AI agent.
  • Delegation and authority definition to the institution.
  • Authorization evaluation to the Control Plane.
  • Enforcement to the Execution Gateway.
  • External execution to the authorized execution system.
  • Evidence collection and outcome verification to the Evidence and Verification subsystem.

The Control Plane must not rely solely on natural-language instructions or the agent's self-reported compliance.

PART II - SYSTEM ARCHITECTURE

7. High-Level Architecture

The proposed system contains the following functional layers:

  • 1. AI Reasoning Environment.
  • 2. Economic Action Request Interface.
  • 3. Identity and Trust Verification.
  • 4. Economic Authority Manager.
  • 5. Policy and Constraint Engine.
  • 6. Execution Decision Engine.
  • 7. Execution Gateway.
  • 8. Revocation and Emergency Control.
  • 9. Concurrency and Reservation Manager.
  • 10. Execution State Manager.
  • 11. Evidence and Verification Engine.

The first two components belong to the request-producing side. The remaining components provide the governance and enforcement functions.

7.1 Logical Architecture

AI Reasoning Environment ↓ Economic Action Request Interface ↓ Identity and Trust Verification ↓ Economic Authority Manager ↓ Policy and Constraint Engine ↓ Concurrency and Reservation Manager ↓ Execution Decision Engine ↓ Execution Gateway ↓ External Execution System

Supporting services:

  • Revocation and Emergency Control.
  • Execution State Manager.
  • Evidence and Verification Engine.

The architecture may implement these functions as separate services or logically isolated modules. Physical separation is not an initial requirement.

8. Trust Boundaries

The architecture defines four principal trust domains.

TB-01: Agent Domain

Contains the AI model, agent runtime, planning logic, and request-generation mechanisms.

The agent is not trusted to define or modify its own economic authority.

TB-02: Control Domain

Contains identity verification, authority management, policy evaluation, and decision logic.

The control domain must be protected from unauthorized modification by the agent.

TB-03: Execution Domain

Contains the Execution Gateway and external execution interfaces.

The agent must not possess an alternative execution credential that bypasses the enforcement boundary.

TB-04: Evidence Domain

Contains event records, execution confirmations, verification results, and integrity metadata.

Evidence records must be protected against unauthorized alteration.

PART III - REQUEST AND EXECUTION PROTOCOL

10. Economic Action Request Model

The proposed request object contains:

  • request_id
  • agent_id
  • authority_id
  • action_type
  • requested_amount
  • currency
  • beneficiary_id
  • target_system
  • idempotency_key
  • created_at
  • expiration_time
  • action_parameters

All fields must be validated according to their declared types and trust levels.

The agent may propose an action and supply request parameters, but must not define authoritative identity, authority limits, policy versions, or verification outcomes.

11. Authorization Decision Model

The Execution Decision Engine returns one of three outcomes.

ADMIT

Indicates that the request satisfies the evaluated authorization requirements.

ADMIT does not establish that execution occurred.

REJECT

Indicates that the request violates an applicable constraint or lacks sufficient authority.

The reason must be machine-readable and auditable.

ESCALATE

Indicates that an additional approval or institutional decision is required.

Escalation must not silently become authorization.

12. Decision Binding

Each authorization decision must be bound to:

  • A unique request identifier.
  • An authenticated agent identity.
  • A specific authority record and version.
  • The applicable policy version.
  • The action parameters.
  • A defined validity period.

A decision must not be reusable for a different amount, beneficiary, action type, or request.

The implementation should use cryptographic integrity protection or an equivalent trusted mechanism for decision binding.

13. Execution Lifecycle

The proposed lifecycle is:

REQUESTED → VALIDATED → AUTHORITY_CHECKED → POLICY_EVALUATED → RESERVED → ADMITTED → EXTERNAL_SUBMISSION_PENDING → EXTERNAL_ACCEPTED → EXECUTED → SETTLED → VERIFIED

Alternative paths include:

  • REJECTED
  • ESCALATED
  • CANCELLED
  • EXPIRED
  • FAILED
  • EXECUTION_STATUS_UNKNOWN

Not every execution system provides separate confirmation for execution and settlement. The implementation must document the external system's actual semantics rather than assume that these states are always independently observable.

14. Idempotency and Replay Protection

The gateway must prevent accidental duplicate execution when requests are retried.

Each economic action must have an idempotency scope defined by the target execution system and the economic operation.

An expired decision must not become valid again through request replay.

The system must distinguish:

  • A duplicate request.
  • A legitimate retry.
  • A new economic action.
  • A repeated external response.

15. Failure Handling

Before External Submission

If identity, authority, policy, or decision verification fails, execution must not proceed.

After External Submission

If connectivity fails after an external submission, the system must record EXECUTION_STATUS_UNKNOWN until reconciliation establishes the actual outcome.

It must not blindly retry an uncertain financial action.

Control Plane Unavailability

The default proposed policy is fail-closed for new actions when authorization cannot be established.

Previously submitted actions must be reconciled separately.

Evidence System Unavailability

The system must define whether to block new execution or use a durable local evidence queue.

Any deferred evidence collection must be recorded and reconciled. The system must not claim successful verification before evidence becomes available.

PART V - PERFORMANCE AND ACCEPTANCE FRAMEWORK

17. Core KPI Definitions

All indicators must have documented denominators, observation windows, and test conditions.

17.1 Unauthorized Execution Rate

Unauthorized Execution Rate =
Unauthorized Executions / Total Executions

Target: 0% within the defined benchmark test suite.

17.2 Authorization Enforcement Rate

Authorization Enforcement Rate =
Correctly Enforced Authorization Decisions / Total Tested Authorization Decisions

Target: 100% in deterministic reference cases.

17.3 False Rejection Rate

False Rejection Rate =
Legitimate Requests Incorrectly Rejected / Total Legitimate Requests

Target: 0% in deterministic reference cases.

17.4 Revocation Enforcement Latency

Measured from the effective revocation event to the enforcement point's rejection of subsequent requests.

Report median, p95, p99, and maximum observed latency.

Proposed initial target:

  • p95 ≤ 500 ms in the controlled laboratory environment.
  • p99 ≤ 1,000 ms in the same environment.

These targets are experimental objectives, not established performance results.

17.5 Execution Decision Latency

Measured from completion of request validation to issuance of the authorization decision.

Proposed initial target:

  • p95 ≤ 100 ms for the reference configuration, excluding external execution latency.

17.6 Concurrent Limit Violation Rate

Concurrent Limit Violation Rate =
Executions Exceeding Aggregate Authority / Total Concurrent Test Executions

Target: 0% in the defined concurrency test matrix.

17.7 Evidence Completeness

Evidence Completeness =
Recorded Mandatory Evidence Events / Expected Mandatory Evidence Events

Target: 100% for the reference lifecycle tests.

17.8 Verification Coverage

Verification Coverage =
Outcomes Successfully Verified / Outcomes Eligible for Verification

Target: 100% for reference cases with complete external evidence.

Unknown or unresolved external outcomes must not be counted as verified.

The proposed architecture must be compared against at least two alternative designs.

Baseline A - Agent-Centric Governance

Governance relies primarily on the agent's internal instructions and application-level behavior.

Baseline B - Integrated Policy Enforcement

Governance uses policy enforcement within the application or execution platform without the proposed independent control architecture.

Candidate C - Independent Out-of-Band Control

Governance uses an independently managed control path and an execution gateway that enforces authorization decisions.

All designs must use equivalent:

  • Agent capabilities.
  • Economic action scenarios.
  • Authority constraints.
  • External execution conditions.
  • Test data.
  • Evaluation metrics.

The comparison must measure both security and operational overhead.

The independent architecture should be considered beneficial only if its measured incremental value justifies its complexity and cost.

23. Known Limitations

The proposed architecture does not independently guarantee:

  • The correctness of an AI agent's reasoning.
  • The truthfulness of external execution providers.
  • The cancellation of irreversible transactions.
  • Complete protection against compromised infrastructure.
  • The correctness of institutional policies.
  • The absence of all authorization errors.
  • Interoperability with every external financial or commercial system.

These limitations must be addressed through integration-specific controls, external verification, security assessment, and operational governance.

26. Conclusion

The Out-of-Band Control Plane is proposed as an architectural approach for separating AI reasoning from independently governed economic authority enforcement.

Its value must be established through implementation, adversarial testing, concurrency testing, lifecycle validation, evidence verification, and comparative evaluation against alternative designs.

The central engineering question is not whether a separate control service can be built.

It is whether an independently governed execution path can measurably improve the enforcement, reliability, accountability, and verifiability of AI-initiated economic actions without imposing unjustified operational complexity.
